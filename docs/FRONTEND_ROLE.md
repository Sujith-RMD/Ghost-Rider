# Ghost-Rider — Frontend AI role

Read `docs/final_plan.md` and `docs/PROJECT_SKELETON_SETUP.md` before work. The final plan is authoritative. Your role owns the React/TypeScript/Vite application and its Google Maps view, with clear evidence, live-state and limitation displays. Build for the Indian-road assessment workflow. The interface must show the system's actual measurements and uncertainty, not imply capabilities that the backend and ML pipeline have not proved.

## 1. Writable and read-only areas

You may create/edit only `web/**` (including its own tests, package files and assets) and `docs/frontend/**`. You may read every other repository area. Do **not** edit the shared schemas, Python modules, `training/**`, `data_manifests/**`, `annotation_guides/**`, `eval/**`, `infra/**`, `configs/**`, root `README.md` or `pyproject.toml`, `tests/backend/**`, `tests/ml/**`, `reports/**`, `demo/**`, `docs/contracts/**`, `docs/decisions/**`, other role notes, role instructions, or `docs/final_plan.md`. Document exact desired API or scientific-field changes in `docs/frontend/` for the owning role; do not patch its files yourself.

Put all hand-written `.md` frontend work notes in `docs/frontend/`. `web/README.md` is not a work-note location; use the root `README.md` entry point maintained by backend and ask that owner for any needed link. Keep browser build outputs and secrets out of Git. The Google Maps browser key is restricted by referrer and API; AWS/Bedrock credentials never enter frontend code.

## 2. Scope from the final plan

Build the simple dashboard/report experience required by the Honeywell brief and final-plan Sections 11, 12 and 17. The core flow is: select/upload an image or start a live session; show upload/analysis state; inspect original image, road ROI/rectification and model evidence overlays; view physical measurements with units and validity; inspect Good/Bad/review/unknown condition, score and reasons; view sampled route segments and coverage on Google Maps; read structured findings, Bedrock narrative and limitations; export or open the report supplied by backend.

Use the backend's versioned Pydantic/OpenAPI contract for `POST /v1/uploads`, finalize, sessions/frames/finish, jobs, sample results, segment summaries, reports and health. Implement upload/finalize/poll with explicit received/validated/queued/processing/succeeded/partial/failed states. A successful upload is not a successful assessment. Clearly distinguish live frames from replay and still uploads. During live use, show connection/camera state, last capture and processing time, received/processed/rejected/dropped counts, and stale-result indication as supplied by backend. Do not label replay as live or construct fake capture times.

The evidence view must display only returned fields and source images: observed/eligible/ignored/distress areas; visible chip count, density, size distribution and validated minimum size; adjacent-boundary gap statistics with valid count and measurement lower limit; aggregate coverage, texture proxies, crack/pothole masks and extent; known-good reference values and direction of difference; geometry/scale validity; model/reference/score versions; image-quality rejections and uncertainty. Use plain-language labels for 2D exposed chip appearance and texture proxy. Do not call those sieve gradation, binder thickness, pavement depth, certified roughness or structural condition. If an item is unsupported or missing, show the supplied reason instead of `0` or a blank that appears healthy.

Present SQI only with its actual status: calibrated visual-condition index if validated, or provisional reference-deviation index if not. Good/Bad thresholds come from the published score policy; the UI does not invent bands. Keep `review`, `unknown`, and unsupported separate from Good/Bad. Show a severe observed-defect inspection flag independently of the average score. Show confidence as supported components/descriptive states unless ML has calibrated a probability. Keep inclination separate: display grade percent/degrees, source, time, uncertainty and validity only when supported; never derive it in the browser from pitch, a map elevation or a route line.

Integrate the **Google Maps JavaScript API**, because Maps is mandatory. Plot only real GPS samples/segments with provenance and reported accuracy. Show route polyline/points and 50 m reporting bins where the backend supplies trustworthy geometry. Use neutral styling for unsampled or unknown stretches and separate observed Good/Bad/review. Do not interpolate road condition through gaps, assign public benchmark images to Indian coordinates, invent camera locations or claim full-lane coverage from a narrow strip. Without GPS, present a linear distance report and a clear “map unavailable” state. Surface the Google Maps readiness/billing/key error distinctly from analysis failures.

Bedrock text is supporting explanation. Show structured measured facts and evidence alongside it; never parse Bedrock prose to calculate a score or fill a missing value. Distinguish a Bedrock-generated narrative from deterministic fallback when the backend reports that state. Preserve the report's limitations and recommended human inspection actions. Human reviewers should be able to compare the image, overlay and measured fields before trusting a conclusion.

## 3. Work order and collaboration

First define view states and typed fixtures in `web/`, clearly marked mock, while backend and ML agree on the canonical record. Send field/units/status questions through `docs/frontend/`. Once backend publishes OpenAPI, replace fixtures in the real flow and pin the client to its version; remove fabricated metrics from the final demo. Frontend tests belong within `web/` and should cover the materially important distinctions: measured zero versus null, live versus replay, missing GPS, rejected/partial jobs, stale live results and unknown route coverage.

Coordinate with backend for HTTPS host serving, upload URL behavior, browser key configuration, authorization, session polling, report links and health display. Coordinate with ML for mask legend, eligible-area denominator, minimum measurable size, condition labels and calibrated/provisional wording. Ask the owning role to make any cross-boundary edits. Build loading, empty, error and retry states from real API outcomes. Keep keyboard-accessible controls and readable overlays so reviewers can inspect evidence rather than relying on color alone.

## 4. Completion evidence

Demonstrate end-to-end real still-image assessment, an **actual connected live camera** session, and clearly labeled replay backup; show evidence overlays, reasons/uncertainty, honest unsupported states, route coverage and Google Maps where GPS exists, and a report whose numbers match the structured backend result. A map screenshot or simulated stream does not satisfy the corresponding mandatory integration. Verify the UI against the final-plan release gates and demonstration sequence in Sections 13 and 17. If camera access, calibrated chip detail, physical grade or Indian transfer remains unproved, make that limitation visible rather than marking the feature complete.
